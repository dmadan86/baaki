## 2. Data model (Postgres)

### 2.0 Migrations & ORM — Prisma

**Prisma is the schema source of truth and migration engine.** `packages/db` holds `schema.prisma`, which under Prisma 7 carries no connection URL at all — the datasource block is `provider` plus `schemas = ["public"]`, and the CLI reads its URL from `prisma.config.ts`. That URL is the **direct (non-pooled)** one: migrations run DDL, and DDL through pgbouncer is a way to lose an afternoon. Nothing at runtime instantiates a Prisma client — the mobile app goes through supabase-js and `/sync`, and the edge functions go through supabase-js as well — so the pooled connection string is a concern for any future server process, not for anything shipping today.

Rules:

- Everything Prisma can express (tables, columns, enums, indexes, FKs, uniques) lives in `schema.prisma`.
- Everything Prisma cannot express — **RLS policies, security-definer functions, triggers, trigger-maintained derived tables (`group_balances`, `pairwise_balances`), CHECK-by-trigger money invariants** — is raw SQL living in the migrations, reviewed like code. A _new_ migration is still written the supported way (`prisma migrate dev --create-only`, edit the generated `migration.sql`, then apply).
- The history has been collapsed. `packages/db/prisma/migrations/` is one baseline, `20260904000000_waves_baseline`, plus whatever has landed since. The baseline is a `pg_dump` of a database with every prior migration applied — the schema in its current shape rather than in the order it was arrived at — with the Supabase role bootstrap prepended (pg_dump omits cluster-global roles) and the persisted reference data appended. A fresh database builds in one step and there is no history to read past. There is deliberately no upgrade path from a database built by the old files: the hosted database was rebuilt from this one.
- The Prisma schema must **exclude Supabase-managed schemas** (`auth`, `storage`, `realtime`) — set `schemas = ["public"]`; never migrate those.
- The generated Prisma Client is for migrations, seeding and the DB test suite — nothing at runtime uses it. The edge functions reach Postgres through supabase-js and security-definer RPCs (`_shared/auth.ts`'s `asCaller`/`asService`), and the mobile client goes through supabase-js (RLS-enforced) and the `/sync` function. Prisma's job here is the schema, not the queries.
- CI applies the migrations forward to a throwaway Postgres 17 and then runs `prisma migrate diff` against _that_ database to guard drift (schema ↔ database). Not a shadow-database replay: `_prisma_migrations` is created by Prisma outside any migration, so a replay asks a question CI cannot answer. There are no down-migrations and no rollback test — the recovery story is rebuilding from the baseline, which is exactly what CI proves on every run.

All money columns `BIGINT` minor units (ADR-003). All tables: `id UUID PK DEFAULT gen_random_uuid()`, `created_at`, `updated_at`. Append-only semantics per ADR-004.

What follows is the ledger's core, not the whole schema — `schema.prisma` is, and it is the thing to read when a column matters. Every table below also carries `updated_seq BIGINT`, the per-group monotonic counter the sync cursor is built on (§4); the personal-scope tables (`captures`, `category_tags`, `personal_records`, `ghost_merges`) carry the equivalent counter on `profiles` instead, because their scope is a person rather than a group. Billing and operator-console tables are described where they are used (§8, §9).

## 3. Core algorithms (`packages/core`)

### 3.1 Split computation

`computeShares(amount, currency, splitType, params, members) → Map<memberId, minorUnits>`

- equal: floor division + remainder rotation — sort members by ID, start offset = `hash(expenseId) % n`, hand out 1 minor unit each until remainder exhausted.
- exact: must sum to amount (validate).
- percent: integer basis points (10000 = 100%), same remainder rule.
- shares/adjustment: weights → proportional; adjustments applied then residual split equally.
- itemized: per-member item subtotals; shared items split equally among claimers (remainder rule); tax/tip/service/discount prorated by subtotal ratio; unclaimed items block finalization.
  **Invariant (property-tested):** `Σ shares === amount` for all inputs.

### 3.2 Simplify debts

`simplify(pairwiseBalances) → transfers[]` — per currency: net each member, greedy match max debtor ↔ max creditor. **Invariants:** transfers ≤ n−1; every member's net position unchanged; deterministic order. Presentation layer only (ADR-009).

### 3.3 Settlement application

Allocations reduce specific expense receivables; unallocated amount applies oldest-expense-first between the pair. Balance views subtract `confirmed + auto_confirmed` settlements; `initiated` shows as "pending" (counted in an "if confirmed" preview, not the headline number).

## 4. Sync protocol (ADR-005)

The client keeps one generic row store, not a copy of the server's shape: `mirror_rows(table_name, id, group_id, seq, json)` holds every synced row as the JSON the server sent, `pending_mutations(client_mutation_id, seq, json)` is the durable queue, `sync_cursors(group_id, seq)` remembers how far each scope has been pulled, and `drafts(key, json, saved_at)` holds half-typed screens. One table rather than twenty means a new synced table costs no client migration.

Every `json` value is encrypted at rest — XChaCha20-Poly1305 with a device-only key in the OS keystore, and per-row associated data binding each ciphertext to its own primary key so a row cannot be moved to another id. `PRAGMA secure_delete = ON` keeps freed pages from holding the old bytes. A row the key will not open is quarantined, never deleted: that ciphertext is the only copy of somebody's offline work, and a key restored later can still read it.

1. Every user action → apply optimistically to SQLite → enqueue mutation (UUID = idempotency key).
2. Sync loop (on connectivity/foreground/push): POST batch to `/sync` edge function → server applies in order, upserting by `client_mutation_id` (replay-safe), returns authoritative rows + a cursor per _scope_ (monotonic `updated_seq`). A scope is usually a group, but four of them are a person: captures, the user's category-tag catalog, their ghost merges and the personal-finance ledger each ride a suffixed key derived from the owner's user id (`personalScope`, `ghostMergesScope`, `categoryTagsScope` in `@waves/core`), occupying the envelope's group slot so one queue and one cursor mechanism serve both. The server pages each table and sets `hasMore` when it truncated one; a client that ignores it syncs the first page and silently loses the rest.
3. Client pulls changes since cursor (also fed live by Realtime), reconciles SQLite, recomputes local derived balances with `packages/core` (must match server).
4. Conflict: two edits to same expense → both become versions; later server-receipt wins as `current_version_id`; loser surfaced in activity feed ("Asha's edit replaced yours — view/restore").

**Not everything rides the queue, on purpose.** Some tables are pull-only in the mirror and written by direct security-definer RPCs: payment proofs and expense attachments (the bytes need an online upload anyway, so an offline queue buys nothing), comments (the RPC is where the role matrix lives — author edits and deletes their own, an admin deletes any, any member flags), the append-only image audit, and ghost merges. The rule is that a write rides the queue when it must work on a plane and its authority can be checked from the payload; anything whose authority is a _role_ is checked in SQL, once, where it cannot be forgotten. Expenses have a second door too — the `expense-write` function, for callers that are already online — and both doors build their RPC arguments with the same function in `@waves/core`, so an online write and a queued write cannot drift apart.

**Never** trust client-computed shares: server recomputes from `split_params` and rejects mismatches (`SHARE_MISMATCH` → client recomputes/repairs).

## 5. UPI settlement flow (ADR-007)

```
Payer taps "Settle ₹420 with Priya"
 → sheet: the rails for this group's country, best first — [UPI] [Bank] [Cash] [Other] in India,
   [PayNow] … elsewhere — + optional expense allocations UI
 → UPI: build upi://pay?pa=priya@okaxis&pn=Priya&am=420.00&cu=INR&tn=Waves%20Goa%20trip
   (validate the handle for that rail; if Priya has no handle on it → prompt her via push to add one,
    or show the QR fallback)
 → Linking.openURL → payer's app chooser → payer returns
 → "Did the payment go through?" [Yes → settlement initiated] [No/cancel]
 → Priya gets push: "Madan says he paid you ₹420 — confirm?" [Confirm → confirmed]
 → No response in 7 days → auto_confirmed (both notified); dispute reopens it
```

**Either party can take it back.** A settlement is a claim about the world, and both people are allowed to say the claim is wrong. The payer can cancel their own — a mis-tap should not become a permanent line in somebody's ledger — and the payee can dispute one, from `initiated` or from `auto_confirmed`, because seven days of silence is not agreement. A disputed settlement is resolved by confirming it or cancelling it; `confirmed` and `cancelled` are the only terminal states. The whole machine is one table in `@waves/core` (`canTransition`), and the same rule is enforced again by a trigger on `settlements`, so a transition nobody wrote a screen for still cannot happen.

Amounts always full precision; `tn` note ≤ UPI limit; iOS: UPI apps installed → same intent works, else show the handle + copy button + QR.

**Seventeen rails, not one (`@waves/core/settlement/rails.ts`).** UPI is the Indian case, not the model. `railsFor(countryCode)` returns a country's national rails first (UPI, PIX, PayNow, PromptPay, QRIS, Aani, PayID, Zelle, Venmo, Cash App, Interac), then the borderless ones (PayPal, Wise, Revolut), then `bank`, `cash` and `other`, which are always last and always offered; `defaultRailFor` is what the sheet selects. A rail says what kind of handle it wants — a VPA, an email, a phone number, a tag, an account — and `isValidHandle` checks it loosely on purpose: the only thing that truly validates a payment handle is a payment, and a validator strict enough to be certain would reject somebody's real account and leave them unable to record a debt they owe.

Only three rails can build a link — UPI an app intent, Cash App and PayPal a web URL — and the rest hand over a handle to copy, which is the ordinary case rather than a failure. A link is refused rather than approximated: Cash App settles in dollars, so a non-USD amount gets no link at all, because a link carrying "25" for twenty-five pounds opens a request for twenty-five of something else, and that is worse than no link.

**Trip reminders (amendment A3).** A group with trip dates gets at most two scheduled nudges a day while the trip is running — "add today's expenses" — through the same §7.1 pipeline as `kind: nudge`, and nothing after it ends. Same rate limit as every other nudge, and the same tone rule: a reminder, never a demand.

## 6. Receipt AI pipeline (ADR-008)

Edge function `receipt-parse`: input `{storage_path | raw_text, group_id}` → membership check → rate limit → monthly scan quota (`waves_receipt_scan_quota`) → per-group receipt cap (`waves_can_add_receipt`), both _before_ the model call, because the point is not to spend the money rather than to notice afterwards that we did → the stored image (already resized to ≤2000px and WebP on the phone) read as service role, with the object path required to start with `${group_id}/` since that read bypasses bucket RLS → Claude vision call with a strict JSON schema →
`{merchant, date, currency, items[{label, qty, unit_price, total, confidence}], subtotal, taxes[{label,amount}], service_charge, tip, discounts[], grand_total}` → arithmetic validation by `checkReceipt` in `@waves/core` (Σ ≈ grand_total, tolerance 1 minor unit; else `needs_review` and the offending lines flagged) → persist to `receipts.parsed`. The model is told not to correct a receipt whose own arithmetic is wrong, because the check only works if it has not silently fixed anything — so `reconciles` is computed here, never returned by the model.
Client review screen: editable line items → publish → group members claim items live (Realtime) → finalize creates the itemized expense via §3.1. Prompt must handle Tamil/Hindi/regional scripts and pasted Swiggy/Zomato/WhatsApp text bills. Track per-scan token cost in a `usage_events` table.

**On-device OCR first (amendment A5).** The phone reads the bill with ML Kit. The platform document scanner (`VNDocumentCameraViewController` / ML Kit) crops and de-skews the page first, because a photograph taken at a table is at an angle on a patterned cloth.

What happens to that text is a ladder, cheapest rung first. A pure parser in `@waves/core` (`parseReceiptText`) recovers the merchant, the grand total and the priced lines from the OCR text by rule — no network, no model, no metered scan — and scores itself with the same `checkReceipt` arithmetic the model path uses, so the caller knows how much to trust it. That is what the capture screen uses, and it is why an amount appears the moment the shutter closes instead of waiting on a round trip. Above it, `raw_text` can be posted to `receipt-parse`, which costs about a tenth of a photo scan and keeps the image on the phone. The photograph itself only leaves the device when the text is not enough — the model understands layout, and a crumpled thermal bill is exactly where rules stop working.

**Scanning from add-expense (amendment A6).** The camera is on the add-expense screen as well as on the itemize screen. From there a scan fills in the **total and the merchant** and stays put — most bills are split some way that has nothing to do with what each line cost — and offers "split by item instead" when it read line items. The parsed receipt is handed over for ten minutes so nobody photographs the same bill twice (a scan is metered, ADR-011).

## 7. Notifications & email (ADR-010)

### 7.1 Pipeline

```
any RPC that changes something ──► waves_notify(...) inserts a `notifications` row
   (kind, recipient, title/body/deep_link/payload, dedupe_key — one row per
    recipient per event, so re-running anything is a no-op)
        │
        ├─(statement trigger on `notifications` → pg_net)──┐
        └─(pg_cron, every 5 minutes)──────────────────────┴─► notify-fanout edge function
   1. claim queued rows — waves_claim_push_notifications / _email_notifications,
      FOR UPDATE SKIP LOCKED, so two overlapping runs never double-send
   2. render each row in the recipient's language (@waves/core; the row holds
      only an English fallback — Postgres has no business holding four
      translations of every sentence)
   3. dispatch push, and email only for the kinds in 7.3
   4. record the outcome; a failed push gets three tries with backoff
```

The trigger is a latency optimisation, not the delivery mechanism. It swallows every error it meets — no Vault secret, `pg_net` missing, anything — because a delivery hiccup must never roll back the expense that caused it. The row stays queued and the cron reaches it either way; the trigger only decides whether that takes a second or five minutes.

Who gets a notification, and on which channel, is decided in SQL by the RPC that raised it and by the claim functions, not by the edge function. The function is deliberately dumb: claim, render, send, record.

Defaults per ADR-010: immediate push only for events **involving me**; everything else folds into a daily group-activity summary. All copy strings are centralized in `packages/core/src/notifications/copy.ts` (en/ta/hi/ar), and a notification is rendered from them at send time rather than at write time: the database row holds a `kind`, a `payload` and an English fallback, because Postgres has no business holding four translations of every sentence, nor any idea which of them this particular person reads. Amounts are formatted from minor units at the same moment, for the same reason — `42000` is not `₹420.00` until you know the currency and the locale, and neither was known when the row was written.

### 7.2 App (push) notifications — Expo

- On login + app-start, register `expo_push_token` into `push_tokens` (one row per device; multi-device supported; revoke on logout).
- `notify-fanout` sends via the Expo Push API in batches of ≤100 and reads the tickets that come back: `DeviceNotRegistered` → revoke the token row; anything else → `push_status = 'failed'` with `push_attempts` and `push_next_retry_at`, three tries with backoff, claimed by the next run. A ticket means Expo accepted it, which is as much as this layer can know — the phone may be off, and saying more in the database would be a lie the UI would repeat. Push _receipts_, which would say what happened after that, are not polled yet. A recipient with no live token is closed out terminally rather than left retryable: no device is a decision, not a failure, and a row that retries forever sits in every future claim's way.
- Every push carries a `deep_link` (`waves://group/<id>/expense/<id>` etc., handled by Expo Router linking config) so tapping lands on the exact object.
- One Android channel today (`default`), and no iOS notification categories. The intent stands and the shape is known — `money` at high importance for owe/settle/nudge, `activity` at default, `digest` low; a "Confirm received" button straight on a settlement-confirm push — but the sender types the channel as a literal, so splitting it is a change in `@waves/core` and the app together, not a config tweak.
- Rate limits: nudges 1/day/pair (enforced in SQL); collapse keys so 5 rapid expenses in one group become one updated notification, not five.

### 7.3 Email — Resend

- **Provider: Resend by default, SendGrid selectable** (amendment A52) — called only from edge functions (`RESEND_API_KEY` / `SENDGRID_API_KEY` in function env, never in the app), chosen with `EMAIL_PROVIDER`. Sending domain ~~`mail.waves.app`~~ **`mail.dmadan.com`** (amendment A28) with SPF + DKIM + DMARC configured before first send; `From: Waves <hello@mail.dmadan.com>`, overridable with `EMAIL_FROM`.
- Templates — plain HTML built in `@waves/core` (`notifications/email.ts` + `render.ts`) from the same copy table the push and the in-app text use, in en/ta/hi/ar with the layout mirrored for RTL. Not a template library: an email carries the same sentence as the push, in the same four languages, and a second rendering stack would be a second place for them to disagree.
  1. `settlement-confirm` — "Madan says he paid you ₹420 — confirm?" (action button deep-links into the app, `waves://` rewritten to the web client for desktop webmail)
  2. `digest` — the daily summary: net waves, per-group deltas, pending confirmations
  3. `nudge` — sent **only** when the recipient has no live device (checked in SQL, where the tokens are)
  4. `group-added` — same condition, plus once a push has exhausted its retries. The one routine event worth mailing: with no in-app inbox, a push that never lands is otherwise the only way somebody learns they were put in a group at all.

  `otp-login`, `group-invite` and `export-ready` were designed and are not built, because nothing produces them: Supabase Auth sends its own OTP mail, invites are links rather than addresses, and export hands back a signed URL in the same response. Adding renderers now would be three untested code paths waiting for a feature.

- Email is **never** used for routine expense activity (that's the Splitwise spam mistake); only the six templates above, each individually unsubscribable via one-click `List-Unsubscribe` + a preferences deep link (transactional `account` mails exempt). Enforced twice on purpose: `TEMPLATE_FOR_KIND` in `@waves/core` and the `kind IN (…)` list in `waves_claim_email_notifications`, so widening it is a change somebody has to make in SQL and mean.
- **Resend webhook** (`email-events` edge function, signature-verified) ingests `delivered/bounced/complained/opened` into `email_events`; hard bounce or complaint → auto-suppress future non-transactional email to that address and flag in profile prefs.
- Idempotency: pass `notification_id` as Resend's idempotency key so retries never double-send; store `resend_email_id` for traceability.

### 7.4 Reminder nudges

User-initiated ("nudge politely") + optional auto-reminders with due dates — both go through the same 7.1 pipeline as `kind: nudge` (push-first; email only if the recipient has no active push token). Always visible to both parties in the activity feed; friendly tone, never collection-agency language.

## 8. Analytics, export, import

- **Analytics (free, basic):** per-group and per-person totals by category/month, exposed as `waves_group_spending(group_id)` — a function, not a view (amendment A7) — at the finest grain: per member, per category, per month, per currency. Currencies are never summed or converted; shares are never re-divided; only current versions of live expenses count. Charts are drawn client-side from plain views, not victory-native (amendment A8) — in the app; the operator console draws with ECharts instead (amendment A31). Deeper analytics = premium later (ADR-011).
- **Categories (amendment A9; extended by A42):** ten built-in categories, guessed from the description with an India-first keyword table and shown as a chip the person can change. Nothing blocks saving; "other" is a real answer. The ten are no longer the whole set — **A42** lets a person add their own tags, and hide or reorder the built-ins, from a personal catalog.
- **Export:** edge function → JSON (lossless) + CSV (locale-aware, includes settlement detail + receipt URLs) → signed download URL. Free.
- **Splitwise import:** parses Splitwise CSV → preview mapping UI (names → members; unknown people become ghosts) → transactional insert as versioned expenses tagged `imported`. Implemented as the RPC `waves_import_splitwise`, not an edge function (amendment A4).
- **Waves import (amendment A10):** the same screen reads our own JSON export back into a new group through `waves_import_ledger`, expenses _and_ settlements, reproducing every balance to the paisa. Ids, edit history and settlement allocations do not come across; none of them changes what anybody owes, and the screen says so before the import runs.
- **Bank SMS import (amendment A2):** ~~built~~ — **withdrawn from the app.** The parser is still there and still tested (`packages/core/src/sms/parse.ts`), but the screen that read the phone's inbox and the Android reader behind it were removed with the rest of the per-group "Bring things in" section, so no message is read on any device today and the app asks for no SMS permission. Bringing a ledger in now means the Splitwise or Waves file on `settings/import` (below), not the message log. A2 records what was built and why it went.

What is missing:

- ~~**The whole Resend half is unbuilt.**~~ Built on 2026-08-09 (amendment A28): the claim/finish protocol, the suppression list, the sender inside `notify-fanout`, the signature-verified `email-events` webhook and a one-click `email-unsubscribe`. 47 tests in `m4-email.test.ts` and 39 in `packages/core/test/email.test.ts`, including the webhook signature against Svix’s published vector. **No email has been sent.** Every one of those tests stops at the edge of the network: what is proved is that the right rows are claimed once, that a bounce stops the next send, and that nobody signed in can reach any of it. What is missing on Android is no longer a console job but a build: no binary containing that file has been made, so no phone has been able to ask for a token, and "payee push with Confirm action → balances update" has never run end to end.

_Since that status was written:_ the mail provider moved behind a seam so leaving Resend is a config change rather than an edit at every caller (A52); the fan-out retries a failed push up to three times before it stops scheduling another (`notifications.push_attempts`); `group_added` falls back to email when the recipient has no live device, which is the first template with a delivery fallback at all; and the fan-out's schedule is now recorded in `docs/notify-fanout-scheduling.md` — it had been deployed with no cron behind it, which is a pipeline that passes every test and delivers nothing. None of that changes the two sentences above: no push has reached a device and no mail has been sent.

Until both are addressed M4 is the largest incomplete block in the project, and the ✓ above should be read as the target rather than the state.

**M5 — AI receipts + analytics + export**
receipt-parse pipeline, review/claim UX, quotas + usage metering, category charts, JSON/CSV export.
✓ English + Tamil + pasted-text bills parse and reconcile; 4 users claim items concurrently; itemized expense math exact; export re-imports losslessly.

_Status (2026-08-08):_ all five parts are built. Bills parsing and reconciling is proved against the deployed function by `e2e/m5-receipts.mjs`; itemized expense maths is a property test in `packages/core`; the export/import round trip is proved balance-for-balance against a real database in `packages/db/test/m5-import-export.test.ts`.

**Four users claiming items concurrently is proved**, by `e2e/m5-claims.mjs` against the deployed project — 27/27 on 2026-08-08. Four signed-in sessions, each having joined through the real invite flow, claiming concurrently through `waves_set_item_claim`; every claim attributed to the caller rather than to whoever the request named. The run also pins the things the criterion implies and nothing tested: the same claim raced four times converges on one row, `NOT_YOURS` refuses claiming for somebody who has the app, `NOT_A_MEMBER` refuses an outsider, the claims table answers a direct client write with `permission denied`, `ALREADY_CLAIMING` freezes the lines once claiming starts, and all four see each other's taps rather than only their own.

**M5 is complete.** All four parts of the criterion now have a proof behind them.

What that harness replaces is worth recording, because it is the reason this went unnoticed for a milestone. `m5-receipts.mjs` carried a check called "four people claim items concurrently without stepping on each other", and it inserted into `receipt_item_claims` through the **service role** — bypassing RLS, bypassing the grants, and never calling `waves_set_item_claim`, the function that decides whose claim a claim is. That table has INSERT, UPDATE and DELETE revoked from `anon` and `authenticated`, so the check drove a door no phone can open, and what it demonstrated was that Postgres accepts concurrent inserts from a superuser. **It has been deleted**, rather than left in place to be read as evidence of something it never tested.

The itemized arithmetic that sat downstream of it stays in `m5-receipts.mjs`, over a claim map written in the file: whether four people can _make_ those claims is `m5-claims.mjs`'s subject, and the sum is the same sum wherever the map came from. With the service-role writes gone, `m5-receipts.mjs` now needs only `ANON_KEY` — everything it does is what an ordinary signed-in phone can do.

**Out of scope v1:** money custody/wallet, ~~SMS auto-import~~ (built, then withdrawn — amendment A2), open banking, ~~iOS widgets~~ (built — A58, and an Android sibling with them), ~~web full app~~ (built — A55's sibling: `apps/web` is a full client, not the guest lite view §9 described), public API, interest-bearing loans (the private ledger tracks a loan's principal against its repayments — A56 — and deliberately computes no interest).

## 11. Non-functional requirements

- Cold start < 2s to usable local data; all list screens virtualized.
- Server recompute of any group's balances < 200ms p95 at 10k expenses/group.
- Crash-free sessions > 99.5% (Sentry); sync queue survives forced kill.
- Accessibility: dynamic type, screen-reader labels on money values ("you are owed four hundred twenty rupees").
- i18n scaffolding from day one: en + ta + hi + **ar** string files; all money/date formatting locale-aware.
  Arabic is more than a fourth column: the layout mirrors, and React Native decides direction natively **at launch**,
  so a language change needs a restart and the app says so rather than half-mirroring. Icons are content, not layout —
  every arrow goes through `directionalIcon`, or "next" points backwards on a mirrored screen.
- Secrets only in edge-function env, and the list has grown with the surface: `ANTHROPIC_API_KEY` (receipt parsing), `RESEND_API_KEY` or `SENDGRID_API_KEY` with `EMAIL_PROVIDER` choosing between them (A52), `RESEND_WEBHOOK_SECRET` and `EMAIL_UNSUBSCRIBE_SECRET`, the four `R2_*` values that are the whole bucket if they leak (A44), `SEND_SMS_HOOK_SECRET` and the four `TWILIO_*` values behind the WhatsApp sign-in code (A61), `SENTRY_DSN`, `ALLOWED_ORIGINS`, `SUPABASE_SERVICE_ROLE_KEY`, and Prisma's `DATABASE_URL`/`DIRECT_URL`. **No LLM, storage, messaging or service key is in the app bundle** — the phone holds no R2 credential and no provider key, which is the whole reason `r2-sign` and `otp-send` exist.

It is **device-local and display-only**, stored on the phone with nothing on the server, and the screen says exactly that in those words. It does not hide you from them, does not leave the group, does not touch a membership and does not move a balance. | §9, §11 | Not in the spec. The honest version of blocking in a shared ledger is small: the money is joint and cannot be unshared, so anything that claimed to cut somebody off would be a lie about a balance that still exists. What it can do is stop a name and a face appearing all day, which is the actual ask. A48 was handed out four times in the same fortnight, to four different pieces of work — the mirror's encryption (the row above), the private ledger (A56), the group tombstone (A49) and the voice cloud-STT meter — and three of those numbers are quoted in source comments. The row above is the one A48 means. The others are renumbered here and the comments will follow; a number that means four things is not a reference, and this is exactly the drift §12 exists to stop.

Two rules that came out of the same period and are binding on new work:

- **A native module is reached through a lazy `require` behind a non-throwing check.** expo-router loads every route file to build the route tree, so a module that throws while its own JS is evaluated does not disable a button — it stops the app from launching, with a red screen naming a screen nobody opened. `TurboModuleRegistry.get` (not `getEnforcing`) and `globalThis.expo.modules` are the two non-throwing forms. Nothing on a dev machine catches this: bundle, typecheck, lint, tests and `expo-doctor` all pass while the app is unlaunchable.
- **Money is converted in decimal, never in floating point.** `0.29 * 10000` is `2899.9999999999995`, and that is one paisa.
- **`is_group_member()` is not an authorization check on a row.** It answers "may you touch this group". A policy that also needs "is this row about you" — is this settlement yours to confirm, is this the author who wrote it, is this your membership row — must ask that separately. Every finding in A16 was this one substitution. And a table nobody's client writes should not be writable by anybody's client: Supabase grants `ALL` on `public` to `anon` and `authenticated` by default, so the privilege exists until it is explicitly revoked, whether or not a policy is ever written for it.
- **`REVOKE ... FROM anon, authenticated` on a function does nothing on its own.** Postgres grants `EXECUTE` to `PUBLIC`, and those roles keep reaching it that way while the statement reports success. It is `FROM PUBLIC`, and then `service_role` needs it granted back.
